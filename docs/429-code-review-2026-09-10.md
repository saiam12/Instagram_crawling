릴스 성공 후 기본 간격 `REEL_SUCCESS_INTERVAL_SECONDS=0.5` 및 기본 직접 수집 동시성 1은 8월 26일과 현재가 같다. 따라서 기본 간격을 최근 줄인 것이 원인이라는 증거는 없다. 데이터 1개 저장과 HTTP 요청 1회는 다르다. 릴스 화면, 작성자 프로필, 지표 보완 페이지, 스크롤 및 Instagram 자체 요청이 함께 발생할 수 있다.

9월 3일 `00d923f`에는 정확한 수치 보완·페이지 재탐색 경로도 추가됐다. 다만 직접 API 요청은 현재 기본적으로 비활성화돼 있으므로 이를 현재 요청 폭증의 원인으로 단정하지 않는다. 이번 수정은 확인된 불필요한 재탐색과 세션 내 동시 실행에 한정한다.

## 운영 시 해석

이 결과는 요청 압력을 늘리는 코드 경로를 재현하고 수정한 것이다. 실제 429 응답의 계정·IP·엔드포인트별 원인이나 Instagram 측 제한 정책 변화는 당시 로그 없이 확정할 수 없다. 기본 JavaScript 버전은 이번 Python 코드 수정의 적용 대상이 아니다.

순차 처리로 겹치는 재수집의 완료 시간이 늘 수 있다. 20분은 프로그램의 대기 정책이며 Instagram이 보장하는 해제 시간이 아니다. HTTP-date 형식 Retry-After는 아직 해석하지 않으며 기본 대기 시간을 적용한다. 서로 다른 프로세스·기기 사이의 통합 요청 제한은 구현하지 않았다. 통합 스케줄러가 신규 탐색 대기 중 도래한 예약 재수집을 우선 실행하는 기존 동작은 유지한다.

운영 검증에서는 같은 계정·실행 모드로 저장 건수뿐 아니라 기존 진단 로그의 실제 네트워크 응답 수, 429 URL/발생 시각, 페이지 이동 횟수를 비교해야 한다. 이미 429가 발생한 세션을 반복 실행해 성능을 확인하지 않는다. 이번 작업에서 실제 Instagram 요청으로 부하 테스트하지 않았다.

커밋·푸시는 수행하지 않았다.

## 검증

- 수정 전 회귀 테스트에서 통합 버전의 재시도 페이지 이동 2회와 공유 세션 작업 2개 중첩을 재현했다.
- 통합 버전 브라우저·스케줄러·회귀 테스트: 240개 통과. 서버가 1,800초 대기를 지정한 경우 예약 수집이 21분 실행 구간 안에서 재시도하지 않는 테스트도 포함한다.
- `git diff --check` 통과.
- Python 버전 전체 실행은 기존 `test_lock_prevents_a_second_writer` 직후 KeyboardInterrupt로 두 번 중단됐다. 기존 `process_is_alive`가 사용하는 `os.kill(pid, 0)`은 Windows에서 POSIX의 무신호 조회로 취급할 수 없다. [Python os.kill 문서](https://docs.python.org/3/library/os.html#os.kill). 이번 429 수정과 별개인 잠금 문제로 기록하며 해당 테스트만 임시 실행기에서 제외해 나머지를 검증한다. 저장소 테스트 자체에는 skip을 추가하지 않았다.

- Python 버전 최종 결과: 176개 중 175개 통과, 위 Windows 잠금 테스트 1개 제외. 회귀 테스트 2개는 모두 통과했다.
